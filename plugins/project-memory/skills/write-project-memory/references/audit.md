# The audit, and what the script cannot decide

`scripts/inspect.mjs` collects the facts a script can read. This file covers
the judgement it cannot make, and how to read what it reports.

## Reading the script's output

The script prints what it found and, at the end, a "still yours" list. Treat
every item in that list as unanswered until you have looked yourself. The
script is deliberately conservative: it reports evidence, not conclusions, and
it never guesses at intent.

Its findings are a starting point, not the audit. The sections below are the
rest of it.

## Package manager

The lockfile that is committed is the answer, whatever any field or README
says. `pnpm-lock.yaml`, `package-lock.json`, `yarn.lock` and `bun.lockb` each
name their manager.

Two lockfiles in one repository is a finding worth reporting, not a tie to
break silently. Ask which one is real, and whether the other should go.

A `packageManager` field that disagrees with the committed lockfile is also a
finding. The lockfile wins, and the contradiction is worth mentioning.

This matters more than it looks. An agent that runs the wrong installer
rewrites the lockfile, and the diff is large, confusing, and easy to merge by
accident.

## Structure that is real versus structure that is documented

Read the tree. A README describing `src/components/` means nothing if recent
components landed in `app/ui/`.

Check where the last several files of each kind were actually added:

```bash
git log --diff-filter=A --name-only --format= -n 200 | grep -v '^$' | sort | uniq
```

Recency beats volume. A directory holding a hundred old files and a directory
holding the last ten additions are telling you different things, and the second
one is what an agent should follow.

Where the two disagree, say so in the recommendation. It is often the single
most useful line in the finished file.

## Conventions the code votes for

Sample real files rather than trusting configuration. A linter rule that is
disabled in half the repository is not a convention.

Worth sampling, in roughly this order of payoff:

- **Test placement and naming** — colocated or in a `test/` tree, `.test.ts` or
  `.spec.ts`. Agents get this wrong constantly and it is trivial to state.
- **Import style** — path aliases versus relative imports, and whether the
  alias is configured in more than one place.
- **File and component naming** — case convention, one component per file or
  several, index files.
- **State and data fetching** — which libraries appear in current code, as
  opposed to which appear in `package.json`.
- **Styling** — the approach actually in use, where more than one is installed.

For each, check whether the pattern holds in files added recently. A convention
the project is moving away from should not be written down as a rule.

## Inconsistency is a question, not a finding

When the codebase does something two ways, do not pick one and write it down.
Report the split, say which way recent commits lean, and ask.

Writing down the losing side of a migration is the most damaging thing this
skill can do, because the agent will follow it faithfully and every file it
touches will move the codebase backwards.

## Commit and branch conventions

Read the actual history:

```bash
git log --format=%s -n 200
git branch -a --format='%(refname:short)'
```

Extract the scope vocabulary that already exists rather than proposing one.
Scopes in use are scopes contributors already type.

If the history shows no convention at all, that is worth saying, but proposing
one is a separate question — ask before adding it, because a commit convention
affects humans as much as agents.

## Generated, vendored and untouchable paths

Find them by evidence, not by name:

- Files with a "do not edit" or "generated by" banner in the first lines
- Output directories named in build or codegen scripts
- Paths matched by `.gitignore` that are nonetheless committed
- Vendored dependency trees
- Lockfiles, which agents should update by running the installer, never by
  editing

For each one, find the command that regenerates it. "Do not edit X" is a
weaker rule than "do not edit X — regenerate with Y", because the second tells
an agent what to do instead of only what to avoid.

## Commands

Separate three kinds, because they belong in the file differently:

- **Routine** — test, lint, typecheck, build, dev. An agent should run these
  without asking.
- **Destructive or outward-facing** — deploy, publish, release, migrate, reset,
  seed. An agent must not run these unprompted, and the file should say so
  explicitly rather than hoping it is obvious.
- **Slow** — full e2e suites, full builds. Worth naming with their rough cost
  and the faster subset to use during iteration.

Verify each command exists before writing it down. A memory file listing
`npm run typecheck` in a project without that script teaches an agent to invent
scripts.

## Existing instruction files

Find all of them: `CLAUDE.md`, `AGENTS.md`, `.cursorrules`,
`.github/copilot-instructions.md`, `.windsurfrules`, `CONTRIBUTING.md`,
`.editorconfig`.

Where two disagree, that disagreement is itself a finding — some agent is
currently following the wrong one. Report it, and in Phase 4 reconcile rather
than adding a third voice.

## The global memory file

If the owner has a global memory file and it is readable, read it. Every rule
it already covers is a rule the project file must not repeat.

Common overlaps worth checking for specifically: commit message format,
branching, code reuse, communication style, general security posture. These
appear in most global files, and in most badly written project files too.

List the overlaps you found when you recommend, so the owner can see the
project file is shorter on purpose.
